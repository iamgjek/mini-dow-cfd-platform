## 問題陳述

這個平台目前的報價與圖表功能是「堪用但陽春」的版本:報價列只有中價/漲跌/一檔 bid-ask,圖表只有線圖/K線切換 + MA 均線,日盤/夜盤雖然已經自動分段但畫面上資訊不完整。使用者要在這個平台上練習台指期交易時,手邊常常還是得另外開一個真的看盤軟體對照(看五檔、看技術指標、看今日高低),沒辦法只靠這個平台完成整個看盤 + 下單的流程,削弱了「練習交易」這個核心價值。

## 目標

1. 報價列資訊涵蓋常見看盤軟體的基本欄位(商品、中價、漲跌/漲跌幅、bid/ask、當盤開盤/最高/最低),讓使用者不用切到別的軟體看基本報價
2. 圖表(K線 + 技術指標)功能達到能練習「看指標進出場」的程度(此部分已有獨立詳細規格,見上方連結)
3. 日盤/夜盤資訊在圖表與報價列上都清楚可辨識,包含目前所在盤次、盤次邊界、上一盤收盤參考價
4. 明確劃定「這個平台不做什麼」的邊界(尤其是外接大盤指數、五檔全部欄位、成交量),避免規格範圍無限擴大,同時把這些邊界背後的技術限制(feed 實際欄位)交代清楚

## 非目標

- **不外接台股加權指數(TAIEX)大盤現貨報價**:平台定位是「微台指期貨」模擬交易,不是大盤觀測站;`price_engine.py` 目前的 feed 帳號也只給期貨商品報價,沒有 TAIEX 代碼可用。如果之後要做,需要另外申請/確認資料來源,列在 P2
- **不保證五檔全部呈現**:README 曾提到 feed 有「真實五檔買賣價量」,但目前 `price_engine.py._handle_line` 實際只解析 36 個欄位中的 3 個(last/bid/ask,各一檔),還沒有解析出五檔全部價量。本規格把「五檔顯示」列為 P1,但**能不能做要先確認 feed 原始欄位裡有沒有其他四檔的價量**(見未解決問題)
- **不做成交量相關功能**(成交量指標、逐筆成交明細):目前 feed 是報價 tick,不是逐筆成交回報,沒有成交量欄位可用,列為 P2 且明確標註「先確認 feed 有沒有這個資料才啟動」
- **不做跨商品/類股比較、新聞、社群功能**:這些是「看盤軟體」的加值功能,不是「模擬交易練習」的核心需求,不在本次規格範圍
- **不做伺服器端運算或指標歷史回測**:延續 [chart-technical-indicators-spec.md](chart-technical-indicators-spec.md) 的決定,指標與報價衍生資訊一律前端即時計算;下方新增的「價格歷史持久化」章節屬於例外 —— 那是資料可靠性(撐過伺服器重啟)問題,不是指標運算,所以需要新增一張資料表,不算違反這條非目標
- **不做跨日/歷史 K 線(日 K / 週 K / 月 K)瀏覽功能**:下方「價格歷史持久化」章節會把資料存進資料庫,但保留視窗只設 48 小時(涵蓋日盤+夜盤還有緩衝),目的是讓重啟後圖表不要空白,**不是**要做多天份的歷史 K 線瀏覽功能 —— 那仍然是非目標,`MAX_TICK_HISTORY`/deque 這類記憶體限制的說明也移到新章節裡

## 時間區間 / X·Y 軸 / 點擊資訊(圖表互動強化)

現況落差說明(對照 `frontend/app.js`):

- ~~**時間區間**:線圖模式已經有 `state.lineRangeSeconds`...~~ 已撤銷,見下方 P0-4 的說明——顯示區間後來交給 TradingView Lightweight Charts 原生的縮放/平移處理,不再用按鈕預先過濾資料
- **X/Y 軸顯示**:Y 軸目前用固定 4 等分(`for (let i = 0; i <= 4; i++)`)畫水平網格線 + 價格刻度,但**X 軸只有文字時間標籤(最多 5 個),沒有對應的垂直網格線**,兩軸的視覺完整度不一致;另外現價(`tick.mid`)目前只在報價列顯示,圖表上沒有一條跟著報價移動的現價參考線,使用者要對照現價在圖表哪個高度得自己目測
- **點擊顯示資訊**:目前只綁了 `chartCanvas.addEventListener("mousemove", ...)` 和 `mouseleave`,完全沒有 `click`/`touchstart`/`touchmove` 事件 —— **觸控裝置(手機、平板)沒有 hover 這個概念,所以在觸控裝置上完全看不到十字線與 OHLC/價格提示框**,這是目前互動設計對觸控裝置的一個明確缺口,不是「錦上添花」而是「功能在觸控裝置上根本用不了」

- 驗收標準:Given 圖表正常繪製,When 檢視畫面,Then 每一個 X 軸時間文字標籤的正上方都有一條延伸到圖表頂部的垂直網格線,且不會蓋過蠟燭/線圖本身(網格線在資料線/K棒下方繪製)

**P0-6:圖表支援點擊/觸控顯示資訊**

- 驗收標準:

  - Given 使用者在觸控裝置上用手指觸碰圖表,When 觸碰發生,Then 顯示對應時間點的十字線與提示框,行為等同滑鼠 hover 的效果
  - 這一項不影響現有滑鼠 `mousemove` 即時預覽的行為,兩種互動方式並存

## 圖表視覺與技術指標優化(對照 tse.php / idx.php)

參考頁面:
- 日盤走勢圖:https://tw.stock.yahoo.com/s/tse.php — 現價貼在 Y 軸右側的實色標籤(隨報價移動)、X 軸取整點時間 + 交替底色帶、Y 軸整數刻度
- 技術分析:https://tw.stock.yahoo.com/t/idx.php — MA 可勾選 + 即時數值 + 漲跌箭頭、技術指標副圖是「一個副圖 + 下拉選單切換」(成交量/KD,J/MACD/RSI/乖離率/…),同時只顯示一種指標,不是多個副圖疊出來

**這裡確認了一個跟 [chart-technical-indicators-spec.md](chart-technical-indicators-spec.md) 不一樣的設計決定**:該文件 P0-1 原本設想「KD/MACD/RSI/布林通道各自獨立開關、可以同時疊出多個副圖」。對照 idx.php 的實際做法後改成:布林通道維持疊加在主圖(跟該文件一致),但 KD/MACD/RSI 改成共用同一個副圖、用下拉選單切換,不再各自獨立開關疊圖。**下面 P0-12 的內容取代該文件 P0-1 的副圖 UI 設計;該文件的 P0-2(公式參數)、P0-3(日盤夜盤分段)、P0-4(持久化的資料存讀方式)維持不變,只是套用到新的單一副圖 UI 上。**

### P0(必須做)

**P0-7:Y 軸整數刻度**
- 目前 Y 軸用 `for (let i = 0; i <= 4; i++)` 把可視範圍硬切 4 等分,刻度數值常常是不規則小數。新增「nice number」取整演算法(1/2/5 × 10ⁿ),依可視範圍自動挑一個好看的間距,刻度數量依資料範圍浮動(通常 3~6 條)而不是固定 5 條
- 驗收標準:Given 圖表可視價格範圍是任意區間,When Y 軸繪製,Then 刻度數值是整數或整十/整百等「好看」的數字,不是任意小數

## 價格歷史持久化(修正盤後圖表空白)

**問題現象**:盤後(日盤收盤 13:45 到夜盤開盤 15:00 之間的空檔,或任何沒有新報價進來的時段),如果後端 process 剛好重啟過(部署、崩潰,或開發時重啟 dev server),圖表會整個空白,顯示「尚無日盤資料」。對照 [日盤走勢圖](https://tw.stock.yahoo.com/s/tse.php):Yahoo 的資料在交易所端,不會因為使用者重新整理頁面或後端重啟就不見。

**根本原因**:圖表資料完全來自 `price_engine.history`(`backend/price_engine.py` 裡的 `deque(maxlen=20_000)`,只存在記憶體),`GET /api/history` 與 WebSocket `snapshot` 訊息都是直接讀這個 deque,沒有任何資料庫持久化。後端一重啟,這個 deque 就歸零;如果重啟後剛好處在沒有新報價進來的空檔,就沒有新 tick 能把它填回來,前端 `findSessionBlock` 找不到今天日盤的任何一筆資料,圖表自然空白。

**決定**(已確認):把價格資料存進 Supabase Postgres 撐過重啟;補齊回來的精細度**每分鐘存一個收盤價就好**,不還原完整開高低收 —— K 線模式下補齊的那幾分鐘蠟燭會是開高低收都等於收盤價的扁平蠟燭,線圖模式看起來完全正常。

### P0(必須做)

**P0-14:新增 `price_history` 資料表**
- `backend/db.py` 比照現有 `SCHEMA_STATEMENTS` 風格新增:`price_history(symbol TEXT, bucket_ts DOUBLE PRECISION, price DOUBLE PRECISION, PRIMARY KEY(symbol, bucket_ts))`(`bucket_ts` 是該分鐘起始的 epoch 秒數,floor 到 60 的倍數)
- 新增三個函式:`upsert_price_points(symbol, points)`(`ON CONFLICT (symbol, bucket_ts) DO UPDATE`)、`get_price_history(symbol, since_ts)`、`prune_price_history(before_ts)`
- 驗收標準:Given 伺服器啟動時呼叫 `init_db()`,When 檢查資料庫,Then `price_history` 表存在且欄位符合上述定義

**P0-15:背景寫入迴圈(不影響即時報價路徑)**
- 新檔案 `backend/history_store.py`,比照 `backend/rollover.py` 的 `run_rollover_loop` 寫法:每 30 秒把 `price_engine.history` 最近一兩分鐘的資料依分鐘分桶(每桶取時間最晚的一筆當收盤價)`upsert_price_points()`,同時 `prune_price_history(now - 48*3600)` 清掉超過 48 小時的舊資料
- 在 `backend/main.py` 的 `lifespan()` 比照 `rollover_task` 的寫法,用 `asyncio.create_task` 多起一個 `history_task`,結束時一併 `.cancel()`
- **刻意不做「每個 tick 都寫資料庫」**:`price_engine._handle_line()` 是同步呼叫所有 listener,若塞一個 blocking 的 psycopg 寫入在裡面,會卡住整個 asyncio event loop、拖慢所有使用者的報價。改成低頻率(30 秒一次)背景迴圈,寫入量小(通常只有 1~2 筆),不影響即時報價路徑
- 驗收標準:Given 伺服器持續運作超過 2~3 個 flush 週期(90 秒以上),When 查詢 `price_history`,Then 有對應 symbol、整分鐘、合理價格的資料列;盤中報價更新速度不受影響

**P0-16:啟動/查詢時用資料庫補齊記憶體不足的歷史**
- `backend/main.py` 的 `get_history()` 改成:當 `price_engine.history` 資料不足(空的,或最早一筆時間距今超過一段閾值,例如 1 小時)時,額外從 `db.get_price_history(symbol, since_ts=now-48*3600)` 撈資料補在前面,用時間去重(記憶體裡的即時資料優先),回傳合併後的清單
- 前端 `state.history` 的資料形狀本來就是 `[{ts, price}]`,資料庫補齊回來的點是同樣形狀,**前端不用改**
- 驗收標準:
  - Given 伺服器重啟且重啟當下沒有新 tick 進來(例如盤後空檔),When 使用者打開頁面,Then 圖表能顯示重啟前的日盤資料,不是空白
  - Given 重啟後接著有新 tick 進來,When 圖表重繪,Then 補齊的歷史與新的即時資料在時間軸上正確銜接,沒有錯亂或重複
